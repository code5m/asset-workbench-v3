# 企业工作区：静态质量候选、源码关系、隔离实验与实例升级

## 使用方法

在业务工作台中依次执行 **发现仓库 → 冻结 Snapshot → Raw 归档 → 质量候选扫描 → 源码候选图 → 隔离优化实验**。操作只针对 Snapshot 中的 Git 提交；绝不向原始公司项目回写。中央工作台「独立工作台管理 → 运行版本与维护」新增全体实例升级预览和带确认的批量升级。

## 可核实的实现范围

- **代码质量候选**：对已归档 Java、SQL、XML 运行确定性规则，定位准确文件、行号和 Git SHA；结果包含风险解释及审核建议。所有发现标为候选，不能当作由大模型完成语义理解。
- **Java/SQL 源码候选索引**：识别部分 Java 类/公开私有方法定义、同类方法调用候选、SQL FROM/JOIN/UPDATE/INTO 明文表名。每条边保存来源 SHA、文件和行号。不会把正则线索称作类型解析准确的 Java Call Graph、MyBatis 动态 SQL 血缘或完整跨服务 Trace。
- **自动优化实验**：目前严格限于去掉行尾空格与制表符；结果保存到独立受管目录，采用 SHA-256 验证，并统计处理文件和减少的空白字节。不会写业务代码，不会伪称已完成 JUnit/Maven/线上收益验收。重要业务逻辑的重构必须经过独立试验、用例和人工或策略许可。
- **Framework 自动升级**：中央发布版本可先生成实例清单及兼容性预览，只有操作者明确确认后才依次更新。某个实例失败就停止继续分发，并尝试回滚该实例。没有全局原子事务，也不能保证所有实例一键升级绝对成功；运行实例需要真实 GUI/E2E 和恢复门禁。

## 上线缺口

真正完成完整语义分析需 Java AST / symbol solver、跨 Maven Module 类路径、SQL 方言及 MyBatis XML 动态解析、调用与数据血缘交叉核验；现在的候选索引不得宣传为这些能力。AI 模型服务未配置，不可将启发式静态规则宣称为大模型自动审查。

自动代码修改与收益验证必须建立可重复的业务构建/测试矩阵、测试影响边界、隔离工作树、审批策略和回滚计划。当前默认仅生成安全、非业务性变更实验结果。

Framework 自动升级的生产标准还需要维护窗口、健康探针、跨实例并发保护、业务兼容性、分批灰度与失败恢复验证；不能把「有升级按钮」视为全部实例完成自动升级。

真实 backV8 的公司业务代码只读；当前阶段的测试在隔离的临时 Git 仓库执行。完整企业生产 READY 需另行验收，不以 CI 通过替代。
